# Maintaining ASPA Explorer

For the people who run the project. Contributors only need [CONTRIBUTING.md](CONTRIBUTING.md).

## The copies of the repository

- **The private project** (on the GitLab of the Department of Information Engineering) is where the project is developed: the CI, the pipeline schedules, the wiki and the releases live there, and the site is deployed from it.
- **The public GitLab project** (`Antonio-Prado/aspa-explorer`) is a copy: a push mirror sends it the protected branches, `main` and `history`, and the tags on every push (work-in-progress branches are not mirrored). The job `publish-release` (every `v*` tag, a protected tag) creates the release there, and `mirror-wiki` (daily, `SCHEDULE=wiki`) copies the wiki, to the public GitLab project and to the wiki of the GitHub copy (with the deploy key of `github-mirror`; the GitLab image sizes `{height=N}` become HTML sizes and the GitLab table of contents is dropped on the way). The links of the README point at the GitHub wiki, which is reachable from outside the department. Both use a project access token of the public project, kept as a masked and protected CI variable; it expires after one year, together with the one used in the URL of the push mirror: renew both.
- **GitHub** (`Antonio-Prado/aspa-explorer`) is the copy where outsiders open issues and send pull requests. The job `github-mirror` (`scripts/mirror-github.sh`) force-pushes `main` and each tag to it with a deploy key that can write to that repository only; the GitHub workflow `release.yml` makes a release for each tag, which Zenodo archives (the DOI is in the README). Its workflows (*Checks*, *Accessibility*, *CodeQL*) run on pushes to `main` and, the first two, on pull requests.

## Applying a pull request

A pull request cannot be merged on GitHub: its `main` is rewritten by the mirror at every push. So:

1. Read it on GitHub and talk to the author there. Ask for changes in the pull request itself.
2. When it is right, take it into the private repository keeping the author: `git fetch <github> pull/N/head`, `git format-patch main..FETCH_HEAD`, and `git am` the patches on a branch of the private project (fix a conflict by hand, not by rewriting the author).
3. Run `make check`, and `make a11y` for a page. Add the line of `CHANGELOG.md` if the author did not, and thank the author in it.
4. Open a merge request, wait for the pipeline, merge, release as usual.
5. Close the pull request on GitHub with a comment that links to the commit. The commit reaches the GitHub copy with the next push.

## Internal merge requests

Whoever has access to the private project: create a branch from `main`, keep one topic for each merge request, make sure the CI pipeline passes and fill in the merge request template.

## Services on the host

Besides the static page, the host that serves it runs a few things that the CI does not deploy, listed here and in the two paragraphs after:

- the builders, from `cron`: the per-AS API, badges and feeds (`scripts/build-api.mjs`, every 15 minutes), the status history (`build-status.mjs`, every 15 minutes), the live watcher of the invalid announcements (`watch-invalid.mjs`, every ten minutes), the comparison of the validators (`build-validators.mjs`, every hour), the RTR session with the validator (`build-rtr.mjs`, every five minutes, from the telemetry of the RTR monitor), and once a day the adoption numbers and the AS registry (`build-adoption.mjs`), the valleys of the 33 collectors (`build-leaks.mjs`), the numbers over time (`build-trends.mjs`) from allocation to ASPA (`build-resources.mjs`) and the other side of the ASPAs (`build-counterpart.mjs`, after the adoption job, whose `relations.json` it reads: the daily copies of the routing registries, without RADb and LEVEL3, and PeeringDB, or its copy at CAIDA when PeeringDB refuses); once a month the dated snapshot (`build-dataset.mjs`);
- the map of the network of the visitor, which nginx answers at `/client-ip` with the address (its `geo` block, `deploy/nginx/aspa.conf`): `scripts/build-client-origin.mjs` writes `/var/db/aspa-gen/client-origin.conf` from the RIPE RIS whois dumps once a day, from root's crontab (`deploy/freebsd/client-origin.cron`), and nginx is reloaded only when the map changed; the file must exist before nginx starts (an empty one will do);
- the services, from `rc`: the notifier, which also keeps the shared results (`notifier/`, `deploy/freebsd/aspa_notify`), the service that creates the tests of the tromboning box on RIPE Atlas (`atlas/`, `deploy/freebsd/aspa_atlas`, with the key of the RIPE Atlas account in a file that only its user can read), and the RTR monitor (`raven rtr monitor` of [RAVEN](https://github.com/nokia/bgp-routing-security-monitor), a Go program built from its source, `deploy/freebsd/raven_rtr`), an independent RTR client of the validator whose telemetry `build-rtr.mjs` reads; the validator must offer RTR to the host, and to nothing else. A **second validator** can stand in for the first: `deploy/nginx/rpki-proxy.conf` sends a request that the first validator fails or does not answer within five seconds to `@rpki_second` in `aspa.conf` (another Routinator, by its IPv4 address when the host has no IPv6, with the name of its certificate in `proxy_ssl_name`), and from there to `@rpki_stale`, the last copy of the first one, whose `proxy_pass` must be the same as in `rpki-proxy.conf` or the copy is not found. The second validator is asked only then, and its answers go through the same cache; the status page shows that it answered (the header `X-ASPA-Validator`). `SECOND_ROUTINATOR` and `SECOND_ROUTINATOR_NAME` in the environment of `build-validators.mjs` add it to *Validators compared* (two requests an hour), and a profile of `raven_rtr` with an entry in the list of `RTR_CACHES` follows its RTR session. The package of Routinator has no supervisor: when its process dies (the kernel kills it when the host runs out of memory) it stays down, so `deploy/freebsd/routinator-watch` (to `/usr/local/sbin`, with `routinator-watch.cron` in `/usr/local/etc/cron.d`) starts it again within five minutes and says so in the system log; `touch /var/run/routinator.nowatch` keeps it stopped on purpose. Fort (the `fort` package, 1.7.0 or later) runs on the host of the validator with `deploy/freebsd/fort-config.json.example`, started by `deploy/freebsd/fortd` instead of the rc script of the package (`fort_enable="NO"`, `fortd_enable="YES"`): in its daemon mode Fort calls umask(0) and leaves its cache and output writable by everybody, so it stays in the foreground under daemon(8) with umask 022; its own user (`fort_user` in `rc.conf`), the TALs fetched once with `fort --init-tals` (ARIN's RPA has to be accepted), RTR version 2 on a port of its own that only the host of the site may reach, `output.aspa` for a JSON of its ASPAs, and the full path of `rsync` (`rsync.program`): the service does not find it in its PATH, and without it every repository that offers rsync only is silently missing, which the validation log at warning level shows. Fort has no web interface of its own: an nginx on its host (`deploy/freebsd/fort-nginx.conf.example`) serves its `output.aspa` over HTTPS on a port that only the host of the site may reach (8324, with the certificate of Routinator, so the script that installs a renewed certificate reloads that nginx too), and `build-validators.mjs` reads it (`FORT_ASPA`), compares it with the other validators and copies it, as Fort writes it, to `/api/v1/fort-aspa.json`. The rc script runs one monitor for each profile in `raven_rtr_profiles` (the site's validators, Routinator and Fort, and the reference caches, such as the public RTR servers of Level66 Network, DaKnObNET and Cloudflare), and `build-rtr.mjs` reads them all from the list in `RTR_CACHES` (`deploy/freebsd/rtr-caches.json.example`); the first of the list is the validator of the site. nginx serves the telemetry of each monitor straight from its directory (`/api/v1/rtr/<id>.ndjson`), its metrics from its endpoint (`<id>.metrics`) and its anomaly baseline from a copy that root's crontab refreshes every five minutes (`deploy/freebsd/raven-baselines.cron`, into `/var/db/aspa-gen/rtr-baselines/`), because the monitor writes the baseline readable by its user only; the incidents detail file is served with `gzip_static`, from the compressed copy that `run-incidents.sh` writes next to it.
- the contacts of the caches that other people run: who lets the site follow a cache can be told of the anomalies of that cache. After they agreed, as the user of the notifier: `node notifier/contact.mjs add noc@example.net CACHE_ID...` (the ids of `rtr-caches.json`; `list`, `remove ADDRESS`). The running service sends a first message that says what they will receive, then the anomalies that it would tell the operator, for those caches only, with what the other caches did at the same time and at most three messages a day and one more that says so; every message has the link to stop. The address is kept like the one of a subscriber and is not published.

They run as unprivileged users; the wiki page *Deployment* describes how to set them up. After changing a file that they use copy it to the host, together with the site modules it requires in a sibling `site/` directory (`site/history.js`, `site/quality.js`, `site/verify.js`, `site/traceroute.js`), and restart the service that uses it. `scripts/build-root-sites.mjs`, which writes `site/data/root-sites.json` for the check of the probes, is run by hand.

The pages read the history of the ASPAs (`history.json`, `events.json`, `visibility.json`) from `/api/v1/archive/`, not from GitLab, which is not reachable from the Internet: `scripts/fetch-archive.mjs` copies the three files from the `history` branch every ten minutes (cron, as an unprivileged user), and nginx serves them.
The messages about the state of the service and about the anomalies of the RTR sessions go to whoever runs the site, not to the public: the notifier refuses a subscription to the topic `status` unless it runs with `NOTIFY_STATUS_OPEN=yes`. To add an address of the operator, start the service with that variable (in the rc script, or by hand), subscribe with `curl -H 'Content-Type: application/json' -d '{"kind":"email","target":"…","topic":"status"}' https://…/api/v1/subscriptions`, confirm the link, and start it again without the variable; the subscriptions that exist go on and can be stopped from their link.

The **Incidents** page has its own small pipeline on the host: the service `aspa_stream` (`deploy/freebsd/aspa_stream`, runs `tools/data_scripts/stream.py` as an unprivileged user, one file for each UTC hour in `/var/db/aspa-data/incoming`) and the hourly job `scripts/run-incidents.sh` (cron, as the same user, five minutes past each hour: it runs `incident-rs` (`tools/incident-rs`, built on the host; `incident.py` when it is missing) on the closed files and then `scripts/build-incidents.mjs`, which writes `/var/db/aspa-gen/incidents.json`). It needs `python3.12` and `py312-websocket-client`. Copy `stream.py`, the binary `incident-rs`, `incident.py`, `extra_detectors.py` (imported by `incident.py`) and `run-incidents.sh` to `/usr/local/libexec/aspa-data/` when they change, and `build-incidents.mjs` (with `build-leaks.mjs`, which it imports) and `rib-links.mjs` (with `mrt.mjs`) to the `aspa-gen` scripts directory; restart `aspa_stream` after a change to `stream.py`. `extra_detectors.py` reads the delegation files of the adoption job (`run-incidents.sh` links them into the working directory), and every threshold of the detectors is a constant at the top of the file that applies it: `extra_detectors.py` for the extensions, `incident.py` for the flapping (`VOL_FO_*`), `build-incidents.mjs` for the full propagation and the persistent valleys (`FP_*`, `PERSISTENT_MIN_HOURS`). The data scripts are a corrected copy of the research scripts of the project (`data_scripts`), with the extensions of `extra_detectors.py` (documented in the `CROSS-CHECK.md` of that project): keep the common part in step.

The collectors that have no recorder are shown from their backfill alone: a directory `collectors/<collector>/` next to `blocks/`, with links to the working directories of that collector (the archive, `days.jsonl` and `cache/` copied here when the worker runs on another host), is read every hour by `scripts/run-incidents-collectors.sh` (its first lines have the cron line), which writes `/api/v1/incidents-history-<collector>.json`, the files of the days and the list `/api/v1/incidents-collectors.json` that the page offers. Every incident file is also kept, compressed, in `/var/db/aspa-data/archive` (`run-incidents.sh` copies it there once), whatever the period the page shows. The days before the recorder was started are read from the archive of RIPE RIS by `tools/backfill/backfill.py` (see its first lines): a working directory with `code/` (`backfill.py`, `worker.sh`, `incident.py`, `extra_detectors.py`, `tools/replay/mrt2records.py`, `scripts/rib-links.mjs`, `scripts/mrt.mjs`), a `venv/` with `mrtparse` (`tools/replay/requirements.txt`), and a list of blocks for each worker (`blocks-NAME.txt`, a line `FROM TO` for each block). A day takes about three hours of one core (some ten minutes to turn the update files into records, the rest for `incident.py`; `tools/replay/check_mrt2records.py` checks the converter against `mrtparse`) and about 2 GB of downloads, which are deleted when the day is done; `days.jsonl` has a line for each day, `touch STOP` ends the workers after the day they are reading, and a worker that is started again goes on from there. Another collector of RIPE RIS is read with `--collector NAME` at the end of each line of the list of blocks, in a working directory of its own (add `rib_links.py` to `code/` on a host without Node.js); small collectors take minutes a day, and a gigabyte or two of memory. The page shows every day that is archived: the last step of `run-incidents.sh` runs `scripts/build-incidents-history.mjs` (copy it to the `aspa-gen` scripts directory with `build-incidents.mjs`), which reads `/var/db/aspa-data/archive` and the working directories of the backfill linked in `/var/db/aspa-data/blocks/` (a link for each, also to a copy of the directory of another host kept in step with `rsync`: `archive/`, `days.jsonl` and `cache/` are what it reads), keeps the result of each file in `days-cache/rrc00/` and the incidents of each day in `days/rrc00/` (served as `/api/v1/incidents/rrc00/<day>.jsonl.gz`), and writes `/var/db/aspa-gen/incidents-history.json`. An incident belongs to the day it ended, whatever the file it is in; when the archive of the recorder does not cover its first days in full, write the first day it does in `/var/db/aspa-data/live-from` (`YYYY-MM-DD`) and let the backfill read the days before; a file is read again only when it changes, and the first run reads them all (some seconds a file).

A backfill machine that can reach the host sends its archives by itself: `tools/backfill/ship-to-aspa.sh`, from a timer every half hour (`ship-to-aspa.service` and `.timer`, for systemd), moves the archives older than 15 minutes to `ship/`, sends them with rsync to `~/ring-archive/<collector>/` on the host and removes them once they are there, after the CAIDA files and `days.jsonl`, which go to `~/ring-blocks/<collector>/`. Its key is one of its own, without a passphrase, and on the host it can do that alone: in `authorized_keys` it has `restrict`, the address of the machine in `from=` and the forced command `tools/backfill/receive.py` (installed as `~/ring-in/receive.py`), which lets through only an rsync that receives into those two directories with `-r` and `-t` (no links, no option that names a path) and writes what it refuses to `~/ring-in/refused.log`. The directories of a new collector, and its link under `collectors/` or `blocks/`, are still made by hand on the host. On such a machine the workers start again by themselves after a reboot: `tools/backfill/start-workers.sh` (as `~/start-workers.sh`), run at boot by `backfill-workers.service`, starts the worker of each line of `~/workers.conf` (`COLLECTOR MEMLIMIT_KB`) that is not running and whose list is not done; it can be run by hand after a line is added.

When a page asset changes (script, style), change its `?v=` as well: the CDN in front of the site keeps assets by address, so the same address keeps serving the old file.

## Scheduled jobs

Four jobs run only from pipeline schedules (variable `SCHEDULE`), on the runner of the host that serves the page; the fourth, `mirror-wiki` (daily, `SCHEDULE=wiki`), is described above. That runner takes only jobs of protected refs, and the rules of these jobs and of the publishing ones also ask for `$CI_COMMIT_REF_PROTECTED == "true"`, so that they fail closed if that setting changes: they hold the protected variables. The `history` branch is protected too, and the scheduled jobs (with the project access token, a Developer) write to it, so a commit there must not bring a pipeline of its own: the CI/CD configuration file of the project is set to `.gitlab-ci.yml@<namespace>/<project>:main`, so every pipeline takes the file of `main`, whose rules start no pipeline for `history`. Changes to `.gitlab-ci.yml` are therefore tried on `main`.

- `host-package-audit` (weekly, `SCHEDULE=audit`): `pkg audit` on the host, including the FreeBSD base system. The job fails, and GitLab sends the usual pipeline-failure email, when an installed package has a known vulnerability for which the repository already offers a fix; vulnerabilities without a fix yet only produce a warning. A daily root cron job refreshes the vulnerability database (`deploy/freebsd/`).
- `aspa-snapshot` (daily, `SCHEDULE=snapshot`): logs the number of ASPAs, provider ASes and the split per RIR as a run of the project's model experiment, so *Analyze > Model experiments* charts the adoption of ASPA over time (`scripts/log-snapshot.mjs`). The same run commits the day's row, events and Atom feed to the `history` branch and the visibility file.
- `history-refresh` (hourly, at minute 20, `SCHEDULE=history`): `scripts/log-snapshot.mjs --history-only` brings only the `history` branch up to date (the day's events and the Atom feed, replayed from the state of the day before), so that the history of an AS and the feed show a new ASPA within the hour and not the next morning. It makes no model experiment run and no RIPEstat call, keeps the coverage figures that the daily run wrote in the row of the day, and commits nothing when nothing changed. A change that appears and disappears between two runs leaves no event. Both jobs write nothing, and fail, when more than 200 ASPAs and more than a tenth of them are gone since the last snapshot (`massRemoval` in `site/history.js`): that is a validator that lost a trust anchor for a while, as on 18 November 2026, and the next run takes the data again. For a removal that is real, run the job with `ACCEPT_MASS_REMOVAL=1`. The notifier applies the same rule to each poll: the poll counts as failed and nothing is announced.

The snapshot and history jobs need a project access token kept as a masked and protected CI variable, because the model experiments API does not accept the CI job token. The token expires after one year: renew it. The history job needs the same token, because writing to the branch is not allowed to the job token either.

Each job can be started by hand from *Build > Pipelines > Run pipeline* by setting the variable `SCHEDULE` to `audit`, `snapshot`, `history` or `wiki`.
